---
name: ship
description: Take one change from the working tree to production — gate on its review, fold and check the branch, make the one commit (fork-change in a fork install), PR, test spend, merge the tested head, deploy and validate, promote on the operator's yes, return to the trunk. `/ship <N|sha>` takes something already on the trunk (a landed port, a change another skill merged) from the deploy on. Operator-invoked only.
disable-model-invocation: true
argument-hint: "[<N|sha>]  — a PR or SHA already on the trunk"
---

Runs only when the operator started it (`/ship`, `/ship <N|sha>`) in this session; a skill that says "run `/ship <N>`" (such as `upstream-port`) never starts it. Every command named below by its key (**Lint changed files**, **Full suite in CI**, **Install deps**, **Full suite (local)**, **Merge method**, **Deploy**, **Deploy URL**, **Promote**, **Health check**) comes from `.omp/rules/commands.md`; `<trunk>` is its **Trunk**. The operator answers the test spend (step 4), "Validated?" (step 6) and the production approval (step 8, or step 5 when the merge deploys production). Anything on a host and cancelling or redispatching a CI run are the operator's hands-on steps: name the step and wait. `.superflow/bin/ship-deploy.sh` does the merge and deploy mechanics and keeps the ship record (`$(git rev-parse --git-dir)/superflow/ship`); its messages name the step to go back to. `g=$(git rev-parse --git-dir)/superflow`.

Fork install (`.fork/CHANGES.md` exists): `ship` reads only the `Fork-Flow-Change` trailer, never `.fork/`'s contents; step 3 runs `fork-change`, and every merge is `--merge`, whatever **Merge method** says. Base install: step 3 makes the commit itself and step 5 uses **Merge method**.

Rules:
- Never run **Promote**, or a **Deploy** that reaches production, without a same-turn ask quoting the sha and the command.
- Production only ever gets the sha that step 6 validated, through step 8; never a build of anything else.
- Roll back only on the operator's request, by the project's own procedure. A migration gone wrong is not a rollback case (the old version runs against the migrated schema): stop and report; the operator decides on restoring data.

## Steps

1. **Situate.** `git fetch --prune origin`.
   - `/ship <N|sha>` for something already on `<trunk>` → step 5, landed path; when the ship record already names it (`pr=` or `sha=`: an interrupted run, or one kept after a no at step 8) → step 6, never straight to step 8: validation runs again and step 7 runs per the record's `tests=` (a `tests=local` recorded by step 7 stands). Fork install on `port/*` → stop: `upstream-port` lands ports.
   - Work on `<trunk>` → `git switch -c <type>/<slug>` first (`<type>`: `feature`, `fix`, `chore`, `refactor`, `ci` or `docs`), then `git branch -f <trunk> origin/<trunk>` if it was committed.
   - `$g/ship-patch-id` is one line, `<branch> <patch-id> <tree>`. Another branch's → `rm -f` it. This branch's → an earlier `/ship` passed the gate (its brief or summary may be gone since): no gate, no `document` below; `.superflow/bin/proof.sh patch-id` must equal its patch-id, a mismatch handled as in step 4.
   - Feature folders: `.superflow/bin/ship-check.sh situate`. This branch's feature → gate: `.superflow/bin/proof.sh verdict features/<slug>/PRD.md --head` (`document`'s gate) must exit 0, else stop: `/flow <slug>` runs the review. Then write `ship-patch-id` from `$g/<slug>/verify/patch-id` (below), then run `document`: it deletes `features/<slug>/`, never `$g/<slug>/`. Another feature's folder, or a file directly under `features/` → stop and ask; never run `document` on it (it would delete a brief never committed).
   - A `$(git rev-parse --git-dir)/diagnose-summary` or `refactor-summary` → ask whether it is this change's (on a resume too: step 4 deletes it). Yes, first run → gate: `.superflow/bin/proof.sh verdict <summary> --fingerprint` must exit 0, else stop: `diagnose` or `refactor` runs the review (a patch-id never replaces an approval). Then write `ship-patch-id` from the summary's `Patch-id:`. A diagnose trigger feeds step 4's PR body. No → leave it (it may be another change's); delete it only when the operator says it is stale.
   - Writing `ship-patch-id`, only right after its gate passed: `t=$(.superflow/bin/proof.sh tree) && printf '%s %s %s\n' "$(git branch --show-current)" <patch-id> "$t" > "$g/ship-patch-id"`. No reviewed change (no feature folder, no summary of this change, no `ship-patch-id` of this branch) → no file; the compares below are skipped, said in the report.
   - This branch's PR (`gh pr view --json number,state,headRefOid`; only "no pull requests found" means none): MERGED → landed path only when the tree is clean and either `git merge-base --is-ancestor HEAD origin/<trunk>` succeeds or (base install, **Merge method** `squash` or `rebase`, which rewrite commit IDs) its `headRefOid` equals `HEAD`; else the name was reused for new work → stop and ask. CLOSED → ask. OPEN → reuse it only when its `headRefOid` equals `HEAD` or is its ancestor, else stop and ask.
   - Commits in `origin/<trunk>..HEAD`. This change's own commit is step 3's: fork install, one with a `Fork-Flow-Change` trailer; base install, one whose subject does not start with `wip:` or `wip(` (`flow`'s checkpoints). None of those and no merges (`git log --merges origin/<trunk>..HEAD` empty) → `git reset --soft $(git merge-base HEAD origin/<trunk>)`. Only this change's own commit (a rerun) → leave it. Mixed, or a merge → ask.

2. **Check.** From the repository root, `git add` each untracked file that belongs to the change first (such as `diagnose`'s new test); prototype and scratch files stay out. Then `.superflow/bin/ship-check.sh` must pass (near tests, **Lint changed files** on the change's paths, no debug or prototype marker). Red (exit 1) → fix. Exit 2 (a check could not run, such as near tests) → stop and show its message; it is never green.

3. **Commit.** Skip when this change's commit exists and the tree is clean.
   - Fork install: run `fork-change`. A tracked edit `fork-change` left out → stop and ask, naming each path: it belongs here → run `fork-change` again; otherwise the operator commits it on another branch or discards it.
   - Base install: every tracked edit in `git status --porcelain` must belong to the change; one that does not → stop and ask, naming each path: the operator commits it on another branch or discards it. `git add -u` plus step 2's new files; anything that looks accidental (secrets, `.env*`, build output, big binaries) → ask before staging it. `git commit` once for the whole change: Conventional Commit subject whose type follows the branch (`feature/` → `feat`; `fix/`, `chore/`, `refactor/`, `ci/`, `docs/` → the same), no AI-assistant attribution, never `--no-verify`; body from `docs/<slug>.md` or the diagnose or refactor summary. A hook fails → fix what it names, re-stage, commit again.
   - Then `git status --porcelain --untracked-files=no` must print nothing. Never stash; do not go on until the tree is clean.

4. **PR and test spend.**
   - `ship-patch-id` exists → before anything pushes (a rebase keeps the patch-id), `.superflow/bin/proof.sh patch-id` must equal its patch-id. Mismatch → show `git diff <tree> -- ':(exclude)*.md'` (the code changed since the review; after a catch-up it also holds `origin/<trunk>`'s new commits) and ask. Yes → rewrite the line with `.superflow/bin/proof.sh patch-id` and `.superflow/bin/proof.sh tree` now. No → stop.
   - `.superflow/bin/ship-sync.sh <branch>` catches up with `origin/<trunk>` (merge when the branch holds a merge commit, else rebase; never rebase a catch-up merge, never `--autostash`) and pushes (a rewritten branch with an explicit `--force-with-lease=<branch>:<old tip>`, never a bare one). Exit 3 (someone else pushed, such as an accepted review suggestion) → stop and ask. Exit 4 → resolve the conflict, `.superflow/bin/ship-sync.sh --continue <branch>`. Fork install: its printed `AGENTS.md` stat must still show the branch's `AGENTS.md` edits.
   - Migrations: the change's migration files (`git diff --name-status origin/<trunk>...HEAD`); read each under step 8's rule. One that drops or renames what the serving version uses → stop: it needs an explicit plan before the merge.
   - No PR → `gh pr create --base <trunk>`, title with a conventional type; show the draft first. Body: a user-facing paragraph; `Closes #<issue>` when there is one; `## How to test` (features) or `## How to reproduce` (fixes); optional `## What changed`; no "how this was tested" section. `## How to test` comes from the current feature doc and the diff, so the feature's own checks and numbers reach the validation in step 6. A fix quotes the diagnose trigger verbatim under `## How to reproduce`. Only once the PR exists, `rm -f` this change's `diagnose-summary` or `refactor-summary`.
   - Ask test spend, recommending from the diff's risk (HIGH: migrations, backend behavior, auth, integration server paths → cloud or local; LOW: docs, copy, small isolated UI → skip may be recommended). Run it to green; red → fix first.
     - Cloud, per **Full suite in CI**: `add label <x>` → `gh pr edit <N> --add-label <x>`, then watch until the full-suite checks (the check names in the key's second value) appear on the head and pass (`gh pr checks <N> --watch --fail-fast`; SKIPPED is not green); `runs on every PR` → the same watch. `no checks reported`, or no check matching a named full-suite check yet, means they have not registered yet, never green: wait and rerun; still none after a few minutes → stop and ask. `none` → cloud is not offered. Suspected flake → ask the operator to rerun it once; an identical second failure (the same failing tests: compare `gh run view <id> --log-failed` of both runs) is real; a failure outside the diff → check the base.
     - Local: `.superflow/bin/full-suite.sh HEAD` (a throwaway worktree: **Install deps**, then **Full suite (local)**). Exit 2 (setup failed, or no **Full suite (local)**) → stop and report; it is neither green nor red.
     - Skip: nothing.
   - `.superflow/bin/ship-deploy.sh record pr=<N> branch=<branch> head=<tested head SHA> tests=<cloud|local|skip>`. Any later push changes the head: record again; the old evidence no longer counts.

5. **Merge.**
   - Unmerged PR: `ship-patch-id` exists → compare `.superflow/bin/proof.sh patch-id` again, as in step 4. **Deploy** `automatic on merge` with **Promote** `none` → the merge is the production deploy, so step 7's gate comes first: the record's `tests=` must be `cloud` or `local` for the recorded head; `skip` or unset → `.superflow/bin/full-suite.sh <recorded head>`, green → `ship-deploy.sh record tests=local`, red → fix, back to step 4. Then do step 8's migration check and ask "Merge now? This deploys production." quoting the head, the tests, those migrations and the PR body's deploy notes and every setting it says to add (a port: its `.fork/PORTS.md` Deploy line and Post-port step), and have the operator confirm production has them; no → stop, the PR stays open. Then `.superflow/bin/ship-deploy.sh merge <N>` (it waits for the checks, merges the recorded head with the merge method, never `--admin`). "back to step 4" (local HEAD is not the recorded head, `<trunk>` moved, the tested head lacks it, or the PR head moved) → step 4; "back to step 3" (a tracked edit) → step 3.
   - Then, and on the landed path (no `gh pr merge`): `.superflow/bin/ship-deploy.sh land <N|sha>`. It checks the PR is MERGED into `<trunk>` (a bare SHA: on `origin/<trunk>`), records the landed `sha=` (the merge commit, or the PR head for a PR landed by push) and re-checks `tests=` against what landed (`unknown` when the evidence does not hold). Any stop → report it; never a candidate.

6. **Deploy and validate.**
   - **Deploy** `none` → report "no Deploy; nothing deployed", step 9.
   - **Promote** `none` → **Deploy** is production: step 7, then step 8. Except **Deploy** `automatic on merge`: on an unmerged PR step 5 already ran the gate and the approval before the merge started the deploy; on the landed path the push started it (a port: after `upstream-port` step 10's approval). Either way skip step 7 and step 8's approval: `.superflow/bin/ship-deploy.sh deploy` only watches the push's CI runs. Exit 4 (no run for the sha) → ask the operator whether it deployed another way (a deployment or status on the commit, their word) or has nothing deployable ("nothing deployed"); a failure → stop and report; then the operator checks production by hand; step 9.
   - Else **Deploy** targets the validation environment: `.superflow/bin/ship-deploy.sh deploy` (`automatic on merge`: watches the push's CI runs; a command: runs it for the record's sha in a clean worktree, **Install deps** first). Exit 4 → ask the operator as above; nothing deployable → no validation, tests or promote: step 9, stop with "nothing to promote". Exit 1 → stop and report.
   - Validation rules: readiness first (the **Health check** against **Deploy URL**); no start, restart, seed, reset or setup snippet there; write only the test account's data; credentials come from the operator (missing → ask) and never go into the repo, a PR or a proof file. Proof comes from **Deploy URL** itself, never a local query, under `$g/validate-<N>/` (`<N>`: the record's `pr`, else its short `sha`).
   - Drive **Deploy URL** with `verify`'s steps 4–5 (omp's own browser, never the operator's; screenshots copied into the folder): login and logout, the app's main path, plus 2–5 probes from the PR body (`## How to test`, `## How to reproduce`, any setting it says to add: check the environment has it) and its files.
   - The operator checks every probe needing their hands (an email, a webhook, a third-party pairing).
   - List `$g/validate-<N>/`, then ask "Validated?" quoting the sha and each result; the report cites only files that list shows. No → nothing goes to production: step 9, then fix forward. The environment moved on to a later `<trunk>` commit (another merge deployed) → `.superflow/bin/ship-deploy.sh adopt <sha>`; re-check what the files it prints need before production (settings, host steps, migrations), then redo this step, probing this change (its PR body and files) as well as the adopted one's.

7. **Tests.** Use the record's `tests=`, which `land` or `adopt` re-checked against the landed candidate. `cloud` or `local` → nothing to ask. `skip`, `unknown` or unset → ask, always with both options, one recommended from the diff's risk as in step 4: run the local full suite, or skip it (the operator's risk). Skip with `unknown` or unset → `.superflow/bin/ship-deploy.sh record tests=skip` (`promote` refuses only `unknown` or unset). Run it on the record's sha: `.superflow/bin/full-suite.sh <sha>`. Green → `.superflow/bin/ship-deploy.sh record tests=local`. Red → nothing goes to production: step 9, then fix forward. Exit 2 → stop and report; it is neither.

8. **Production.** First what production has not run yet (done in step 5 when the merge itself deployed production): production's commit `p` (the operator's word, or the release tag or marker the project keeps); `git diff --name-status <p> <sha>` over the migration files lists every migration going out, not only this PR's. `p` unknown → review this change's own migrations and say that only those were checked. Each must keep the serving version working on the new schema (`AGENTS.md`: schema changes stay backward-compatible); one that drops or renames what that version still uses → stop: it needs an explicit plan, and after it a rollback is no recovery.
   - **Promote** set: ask "Promote now? This is the production approval." quoting the sha, the **Promote** command, the migrations and the PR body's deploy notes and every setting it says to add (a port: its `.fork/PORTS.md` Deploy line and Post-port step), and have the operator confirm production has them. Yes → `.superflow/bin/ship-deploy.sh promote` (it refuses `tests=` unknown or unset, and runs **Promote** for the sha in a clean worktree).
   - **Promote** `none`, **Deploy** a command: ask "Deploy to production now? This is the production approval." quoting the same. Yes → `.superflow/bin/ship-deploy.sh deploy` (the same refusal). (**Deploy** `automatic on merge` never gets here: step 6 handles it.)
   - No → stop: no step 9, the record stays, so a later `/ship <N>` resumes at step 6 (step 1). A failure → stop and report; roll back only on request. Then the operator checks production by hand.

9. **Return.** Only after the merge, on the landed path, or after "nothing deployed" or "nothing to promote"; never before, never after a no at step 8. `.superflow/bin/ship-deploy.sh done`: it checks the record's `branch=` is merged (fork install or **Merge method** `merge`: its local and remote tips are in `origin/<trunk>`; `squash` or `rebase`: the PR is MERGED at the recorded head, which both tips equal), switches to `<trunk>` with `git pull --ff-only` (refused → stop, never reset), deletes only that branch, never whichever branch is checked out, and the feature's `$g/<slug>/`. A mismatch → stop and report; the branch holds work the merge did not take. Then `rm -f "$g/ship-patch-id"`. Report PR, sha, tests, what was deployed and promoted, and where it stopped: one line per field, then the stop point.
